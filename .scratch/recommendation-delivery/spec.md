# 统一套餐推荐、办理入口和后续指代

## 现有问题

BN 运行 `c6436cc4` 中，需求提取理解了 1G 和月费低于 $198，也通过地址可售范围和原文核验选出了 `AX9836ROB`、`AX10924DB`。提取节点仍把请求归为 `availability`，且 `catalog_recommendation` 为空。正文比较了两款套餐，办理节点却输出 `NONE`。前一轮已修复地址回传时的空消息问题，本轮暴露的是另一处规则，办理入口仍依赖模型是否另填一段推荐原话。

现有 `turn_intent` 同时决定筛选范围、需求是否长期保存和用户最后看到的内容。初筛的 `action: recommend` 还同时用于开始筛选推荐和查找套餐事实。后续 `record_reply` 有时依赖办理列表，有时在自由正文里搜索编号，也可能继续保留更早的推荐编号。这三个节点可以对同一轮给出不同结论。

## 请求理解

使用两项独立判断，模型在需求理解节点输出，代码校验其结构、业务及来自用户的证据。

| 判断 | 取值与效果 |
|---|---|
| 本轮交付目标 | 选出可供客户选择的套餐、回答事实或可售性、索取指定套餐的入口。明确要选、按自身条件找更实惠的方案，以及明确要查看某款的条款，分别按其目标处理。 |
| 需求作用范围 | 本轮临时条件、沿用已有选购条件、明确修改已有选购条件。临时选购同样可以生成推荐和入口。 |

「我需要 1G，月费有冇得平」的目标是按条件找选项，月费可以仅用于本轮筛选。「呢款月費幾多」的目标是核对某款事实。「有冇自動續約」要根据上下文定位套餐或澄清对象。泛问是否提供某项服务时，先答事实。存在足够上下文时，疑问句形式和「推荐」二字都不决定交付目标。若客户既想选套餐又问具体条款，保留两项要求并分别核对。

## 地址和澄清

- BN 缺地址时，保存当前选购请求的业务、交付目标、有效条件及待完成状态，然后触发地址表单。澄清事件也要保留原请求，合并新增答案。
- 收到地址结果时，恢复与此次地址查询关联的待处理请求。地址回传文本用于识别事件。业务条件和交付目标来自原请求及客户随后明确的修改。
- 地址变更时，先使旧范围和相关展示结果失效，再依据当前地址重新核验套餐。有活跃选购目标时继续原目标。仅核对覆盖或单款套餐可售性时，交付查询结果。
- 地址上下文必须在生成结果和前端展示两个时点都有效。复用现有 `qid` 或受信的等价查询标识来绑定范围。当前工作流只有 `bn_plan_codes`，标识的传递与校验需要工作流和前端共同接入。重复回传按事件关联标识去重，过期地址结果不覆盖新范围。

## 统一展示结果

在精筛核验之后、任何面向用户的输出之前，生成一份由代码确定的展示结果。该结果包含业务、交付目标、状态、按展示顺序排列的已核验套餐，以及适用的地址查询引用。各消费者读取同一份结果。

| 核验结果 | 正文 | 办理入口与指代 |
|---|---|---|
| 找到可供选择的套餐 | 给出实际选中的套餐及取舍 | 为可办理的套餐按展示顺序生成入口。记录展示编号及顺序。 |
| 只查询可售性、单款事实或条款 | 按问题回答，可以列出已核验的事实对象 | 默认无办理入口。查询结果允许定位明确提及的套餐。 |
| 明确索取某款套餐的入口 | 回应指定对象 | 仅在当前范围内能唯一定位且核验通过时生成一项。 |
| 需地址、仍有歧义、无匹配或核验失败 | 说明当前结果及适当的下一步 | 无办理入口。无匹配时仍可回答有当前证据的独立咨询。 |

精筛前的候选只用于核验。只有通过当前业务、可售范围和原文核验的套餐进入展示结果。BN 必须使用当前地址范围。正文的套餐标题、编号和顺序来自展示结果，宜由模板或产品卡片渲染。模型用来表达用户关心的取舍。动作节点仍输出 `frontend_action`、`service_type` 和 `products`。

后续「第二款」按最近相关的展示结果解析，普通咨询不覆盖上轮推荐的顺序。明确回指旧推荐时，先校验当前可售范围，再给入口。地址变更、选购目标切换或核验失败时，旧结果不得接替本轮结果。

## 接入与迁移

1. 用完整运行记录建立场景回放。让需求理解输出交付目标和需求作用范围。现有会话状态仍可读取，逐步撤掉链接逻辑对 `catalog_recommendation` 的依赖。
2. 让代码从精筛结果生成展示结果。推荐版式、动作和会话指代都改读这份数据。保持现有 SSE 输出字段，减少前端接入变动。
3. 接入 BN 地址查询标识和事件关联。前端按当前运行及查询标识关联结果，忽略过期事件。Langfuse 记录交付目标、精筛及展示编号、动作输出和无入口原因。接入方分别记录事件是否收到以及是否成功渲染。

## 验收场景

| 场景 | 预期 |
|---|---|
| 需要 1G 和更实惠方案，随后提交地址 | 使用地址范围内的匹配套餐。正文、入口和会话记忆的编号及顺序一致。 |
| MS 想看高流量计划，XE 说想找约某金额的独立订阅 | 选购目标跨业务一致。临时条件可以产出推荐，并且只在客户明确时更新长期需求。 |
| BN 只查某地址能否安装指定套餐，或问上轮第二款是否自动续约 | 直接核对可售性或套餐条款。无需自动展示入口。 |
| 提交地址后立即改地址，两次结果乱序返回 | 只展示当前地址的结果。旧套餐即使曾有入口也无法复用。 |
| 先推介两款，再问第二款的条款，随后要第二款的链接 | 指代保持一致。索取链接时再次核验可售范围。 |
| 客户只说「嗰款」，同时有两款合理指代 | 请求澄清。套餐对象唯一后才返回入口。 |
| 本轮无匹配或精筛失败，上一轮有推荐 | 当前轮无入口。历史结果不会补成本轮推荐。 |
| 工作流输出入口，前端缺 `qid` 或 SSE 中断 | 状态可区分。前端不会展示无效跳转。 |
