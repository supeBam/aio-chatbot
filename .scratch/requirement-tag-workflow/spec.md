# Dify 需求理解与推荐流程

> 历史规格。独立的 [多业务原型](../aio-multi-business/spec.md) 已支持 MS 和 XE，
> 按业务隔离偏好，并增加 BN 地址可售资格检查。
> 本文描述早期设计，不适用于该原型。

## 范围

Dify 对话工作流通过多轮对话理解用户需求，
在生成后端查询前要求用户确认识别出的业务类别，
并从后端提供的候选列表中推荐最多 3 款套餐。
后端筛选和排序不属于本次早期设计的修改范围。

支持识别的类别：

- `BN`：固定家居宽带服务，包括网速和宽带套餐需求。
- `OTT`：独立的流媒体或数字内容订阅。
- `MS`：可识别为移动通讯，但此早期设计尚不支持；应说明范围限制，不提交该业务。

宽带附带的流媒体服务仍属于宽带套餐需求。
如果用户既可能指宽带组合，也可能指独立 OTT 订阅，应询问其意图，不自行猜测。

## 会话状态

保留一个扁平状态，不按业务类别建立独立的需求对象：

```json
{
  "schema_version": "2.1",
  "business_categories": [],
  "business_category_confirmed": false,
  "scan_tag": [],
  "plan_tags": [],
  "uninterested_plan_tags": [],
  "uninterested_scan_tag": [],
  "bandwidth_mbps": null,
  "monthly_fee": null,
  "contract_months": null
}
```

数值约束为 `null` 或 `{ "operator": "lt|lte|eq|gte|gt", "value": number }`。
带宽单位为 Mbps，月费单位为港元/月，合约长度单位为月。
`gaming`、`streaming` 等正向使用场景标签存入 `scan_tag`；
`netflix`、`router_wifi7` 等正向套餐权益标签存入 `plan_tags`；
明确拒绝的套餐权益标签存入 `uninterested_plan_tags`。
`uninterested_scan_tag` 只保留从旧状态结构迁移的负向场景标签，提取器不得新增该字段中的条目。
同一标签类型内，一个标签不能同时具有正向和负向态度。
用户未提及的状态应跨轮次保留。

LLM 提示词使用自然语言定义 BN、OTT 和 MS，使模型能够从自然表达中推断类别。
从对话中推断出的类别仅作为建议，只有用户明确确认类别摘要后才视为已确认。
类别发生变化时，需要重置确认状态。
重复提出相同类别不能重置状态；仅增加需求的轮次不能被推断为用户已明确确认类别。
类别尚未确认时，不得生成后端查询。

需求提取和推荐 LLM 节点均使用带有明确结构定义的 Dify 结构化输出。
对应 Code 节点直接使用 `structured_output` 对象，不解析 LLM 的自由文本。
仍需通过代码校验证据、状态迁移、类别确认，以及 `plan_code` 是否属于候选集合。

## 推荐流程

后端返回候选套餐 JSON 后，由独立的 LLM 推荐分支结合对话历史和扁平状态，
选择最多 3 款合适的候选套餐。只能推荐候选列表中存在的套餐。
Code 节点校验输出结构、数量上限、唯一性，以及 `plan_code` 与候选的精确匹配关系；
不得修复或编造编号。选中的编号必须与候选记录中的原始编号完全一致。

## 验收检查

- 多轮对话可以累积感兴趣、不感兴趣标签和数值约束，不丢失未提及的值。
- 能从描述和别名理解 BN、OTT；宽带附带服务与独立 OTT 订阅存在歧义时进行澄清。
- 明确说明此早期设计不支持 MS。
- 用户明确确认类别前不生成后端查询；拒绝或更改类别后需要重新确认。
- 推荐分支最多选择 3 款候选套餐，拒绝不存在、被改写或重复的套餐编号。
