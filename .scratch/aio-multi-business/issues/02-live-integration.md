# 对接现有前端与真实后端

状态：待处理
阻塞原因：缺少实际部署环境的 API 和前端源码信息

## 范围

遵循 [原型接入协议](../spec.md)，定位现有前端地址表单和聊天网关，
实现两个独立开始节点字段和三事件，`query` 保留自然语言。
地址查询后直接传入逗号分隔的可售编号，不额外引入地址查询记录 ID。
将批量标签、排序详情两个模拟接口替换为经过鉴权的后端服务。
验证目标 Dify 实例的导入兼容性和真实模型表现。

## 验收条件

- Dify 凭据仅保存在服务端。
- 验证目标 Dify 实例在同一会话下能读取每轮更新的 `inputs`。
- 可售范围属于同一用户、同一会话和当前地址版本，不信任浏览器或模型提供的编号。
- 后端串行处理同一会话的请求，并拒绝过期回调。
- 提交表单后自动继续同一个 Dify 会话。
- 普通聊天显式传 `message` 并清空地址字段，不重复处理旧事件。
- 真实模型不能将地址提交或标签加载视为需求已就绪。
- 有效标签数组可以跨轮次复用，访谈阶段不调用排序详情接口。
- 前端明确处理所有动作，以及流式响应截断或报错的情况。
- 收到 `address_action` 成功完成事件后立即转发表单动作，不依赖可能被隐藏的 `outputs`。
- 自然语言 `message` 分片直接显示，不再缓冲并解析业务 JSON。
- 等待 `workflow_finished` 再执行下一轮，避免回复后的状态保存被并发请求覆盖。
- 用真实模型验证用户背景更新保留未提及事实、明确改口和证据出处。
- 后端返回未知套餐编号时，绝不能扩大候选范围。
- 真实地址、无覆盖、服务失败和业务切换均通过端到端检查，不再使用模拟数据作出可办理承诺。
