# AIO 三业务显式状态与流式回复规格

## 1. 当前方案

本版按最新讨论重新实现，包含：

- [Dify 对话工作流](../../dify/AIO%20Multi%20Business.txt)。
- [生成脚本](../../dify/build_multi_business_workflow.py)。
- [字段与状态说明](fields.md)：所有入口、会话变量、对象字段、模型协议及节点输出。
- [流程与节点说明](flow.md)。
- [本地执行测试](../../tests/test_aio_multi_business_workflow.py)。

原有 [BN 测试工作流](../../dify/AIO%20Demo.txt) 不修改。
当前产品服务仍由 Code 节点内嵌数据模拟，不代表已接通真实后端或前端。

### 与旧版的差别

1. 只有 `message`、`address_add`、`address_change` 三个事件。
2. 入口只有 `event_type` 和 `bn_plan_codes`，不再传 BN 查询状态或地址查询记录 ID。
3. 不再保存 `aio_state_json`，改用明确命名和类型的会话变量。
4. 标签缓存、用户偏好、使用背景、访谈就绪分别保存，互不混淆。
5. 所有聊天回复直接流式输出 LLM 自然语言，不再包装成业务 JSON。
6. 弹地址表单时，前置 Code 节点先输出 `request_address` 动作，LLM 同时负责后续引导话术。
7. 复用需求提取模型生成 `user_context`，不增加独立的背景摘要模型调用。
8. 用户需求独立保存为自由文本及原话，不依赖产品标签词表；按需求ID修改或撤回。
9. 精选逐条核对用户需求与套餐原文，区分支持、不支持和未知，并校验引用出处。
10. 产品分析在访谈分支之前统一决定是否追问；动态问题基于产品差异，不设最低访谈轮数。
11. 所有模型共享产品与安全边界，最终回复不读取全量目录，降低未执行推荐时自行编造套餐的风险。
12. 追问不再要求精确标签引用，不新增引用ID；按自由标签语义初筛，代码只按选定套餐编号取得对应原文。
13. 独立条件按R编号保存，并区分明确要求、偏好及未声明强度；事实咨询按Q编号保存，也影响候选查找，但不自动成为硬性购买条件。
14. 精选每款套餐对每个R编号恰好评估一次，对每个Q编号在 `info_answers` 中恰好回答一次；资料未提及不等于不包含。最终回复保留上下文，自然先回应最新咨询，不展示内部编号。
15. 旧会话补齐咨询字段而不丢失已有需求；旧复合需求整体核对一次，不猜测拆分。重复、越界和缺失错误含套餐与ID，通过现有有限重生成纠正，不静默删除冲突评价。
16. 同一维度已有明确值时，后续互相冲突的新具体值默认更新原R编号，不要求用户显式说“改口”；用户明确比较多个情境时才并列新增。“有什么推荐什么吧”在目标规格缺货后放宽该维度，保留其余要求。
17. 目录没有精确规格不等于没有相关方案；用户愿意比较时初筛应选同业务最接近的可售替代并披露差距，不因规格不匹配直接给空列表或归入boundary。

## 2. 业务边界

| 业务 | 产品范围 | 前置条件 |
| --- | --- | --- |
| BN | 家居宽频 | 后端根据地址得到的可信可售套餐范围 |
| MS | 移动通讯 | 无地址前置条件 |
| XE | 独立影音、音乐和 XE 目录内旅游数据等产品 | 无地址前置条件 |

宽带或手机套餐附带影音权益仍属于原业务，不因出现 Netflix 等词语自动切换 XE。
可以记录多个业务的需求，但一轮只聚焦一个业务，不做跨业务组合计价。
提及不等于购买任务：`mentioned_businesses` 不再驱动消息广播；无明确分片时只写当前业务。
只有明确同时独立购买多个业务时，使用 `business_requests` 按原话片段分发，不把整句跨业务复制。
分片出处、目标、重复和容量校验在提交前完成；业务切换不向旧业务追加待处理消息。
提取变更每项必须声明当前业务，显式外业务条目拒绝保存；模型误标业务语义仍需在线评测。
各业务模型只接收当前业务的需求、背景和候选，不使用全局聊天记忆混合业务。
一般概念咨询不调用产品接口，也不强制填写地址。

### 高级销售顾问边界与统一展示

顾问只依据提供的套餐资料介绍速度、流量、费用、合约、服务内容和相关特色。
不得主动追问运营商，不提及其名称，不评价、比较网络优劣、信号、排名或口碑；
即使用户主动提供名称或诱导比较，也不复述相关话题，直接回到可核实的套餐事实。
必要时只说明“我可以根据套餐资料帮您比较流量、月费和合约”。

MS 已删除 `network` 访谈主题。运营商名称与偏好不作为产品需求收集；
用户提供其他公司的报价并询问能否更便宜时，保留中性价格目标及咨询，不误当成品牌偏好：
例如保存“希望月费低于$198”，原话证据仍保留完整引用；报价不自动成为硬性预算。
若模型在需求或咨询文本中保留品牌，该条目不保存，转为明确的品牌边界回复而非内部错误；
纯品牌需求不执行推荐，同句合法需求和咨询继续处理，并明确说明含品牌条目未保存。
不由代码猜测改写价格，不以默认值冒充处理成功；提取模型仍应优先将报价记录为中性价格目标。
排序请求忽略旧运营商偏好，精选模型也不能据此选择套餐。
原始目录和文档不修改，内部校验仍使用真实编号和原文。
供精选和最终回复使用的销售展示视图移除名称、身份标签及相关话题，
保留流量、价格、合约、限速、收费和自动续约等关键事实。
`HKBN SAFE` 作为独立产品权益在展示中改称“网络安全服务”，不把该权益当成运营商偏好删除。

BN、MS、XE 的推荐统一使用以下结构，只有一款也不能合并成大段：

```markdown
##### 1. 中性套餐名称（套餐编号）

- **核心内容**：主要速度、流量或订阅内容。
- **月费与合约**：月费、合约、预缴和必要收费。
- **相关特色**：与用户相关且有原文依据的附加内容。
- **取舍提醒**：限制、未知条件和偏好缺口。
```

多款之间留空行，最后简短对比，不重复罗列所有赠品或写冗长总结。
所有分支的最终回复如使用 Markdown 标题，最大只使用五级标题 `#####`，允许六级 `######`；
禁止一至四级标题、Setext 下划线标题和 HTML 标题标签，套餐标题统一使用五级。
该约束由最终回复提示词和推荐模板实现，保留直接流式输出；实际模型遵守情况需线上验收。
标题使用展示视图的 `display_name`，不补回原文中被移除的名称。
仍由同一个 LLM 自然语言流式生成，模板和行为边界需在目标模型上验收；
本地测试能验证展示上下文、格式指令和数据保留，不能代替在线话术验证。

用户只说“本地流量卡”时，不得推断 100GB；某款套餐的 100GB 只能称为产品规格，
不能据此说用户已明确需要 100GB。
弹性生效日期也不代表短合约或提前解约权，不能用启动灵活性掩盖合约期限缺口。

## 3. 前后端调用协议

### 提示词结构与相对需求验收

五个主 LLM 节点及四个仅失败时运行的重生成节点的 system 提示词统一按业务前提、安全与事实边界、角色与任务、决策步骤、输出契约分节；
user 提示词按本轮输入及具体数据来源分节，JSON 输出协议保持不变。
按 prompt-engineering-patterns 技能加入与各节点实际协议一致的少样本输入输出；路由、提取、初筛与精选示例提供合法JSON，回复示例只示范开头，不替代完整推荐版式。
JSON示例使用裸JSON，不带Markdown代码围栏，避免模型把围栏误当输出格式。
业务路由、需求保存、产品决策与精选校验共用严格的模型JSON解析入口，仅容忍外围空白、BOM和完整包裹单个对象的JSON或无语言代码围栏。
空输出、截断JSON、额外说明、多对象、非JSON语言围栏及结构不合规仍明确失败，不提取正文中的大括号片段、不自动补字段或返回默认推荐。
空输出会明确提示检查上游LLM的text及结束原因；语法错误报告行列位置，业务结构、用户证据、可售范围校验不变。
产品决策已明确为recommend或boundary且仅省略follow_up时，代码规范为null，避免无追问动作因省略空字段而失败；不默认动作、候选或理由，不补造追问，其他未知字段、真实需求歧义及范围校验保持不变。
初筛编号是不可改写的标识符，须保留完整下划线后缀。越界错误须列出无效编号及本次目录的完整允许编号，供既有的一次重生成纠正；不按前缀自动补号、不静默删除错号或扩大范围，重试仍不合法则继续拦截推荐。提示词和替身回归不能保证真实模型一定纠正。
精选提示词要求逐套餐对象仅输出plan_code、requirements和info_answers，总理由放在顶层reason；无咨询时兼容省略info_answers。校验器额外兼容逐套餐字符串reason并丢弃，不将其作为事实，也不忽略任意未知字段。
MS流量回答“不清楚、随便”应保留为已回答信息，不能因额外说明文本中断推荐；此格式兼容仍必须通过候选范围、逐需求覆盖校验。
产品 `quote` 允许原文摘录或准确转述，不以逐字、标点、简繁体、列表前缀或行序匹配作为成功门槛；
不再恢复或强制替换成原文片段。用户原话 `evidence` 的精确出处校验仍保留，两者不可混淆。
按用户选择不增加独立事实核对节点：精选与最终回复模型仍依据对应 `markdown` 核对金额、期限、
收费前提与权益归属，代码不证明转述事实正确。没有事实依据应为unknown，不将非空依据当成真实保证。
预缴不等于押金，月费$0不代表零额外费用；原文未说明可退或抵扣时，不推断为押金、不构成额外购买或无需额外费用，必须披露金额及未知条件。
示例使用虚构的 `DEMO_` 编号且明确禁止复制到实际候选，用户原话、目录标签、产品正文分别承担意图、检索、事实核对职责。
需求提取保留“相对上一轮推荐”的对象与调整方向；初筛和精选读取显式比较上下文，先确定基准再比较产品。
能确认反馈时比较对象的，在自由需求中固定该对象；后续只补充预算等信息时不得自动把旧比较基准滚动到最新推荐，避免无故反复提速。
上轮三款均为 1000M 后用户反馈“带宽太慢了”，且目录包含更高速候选时，应优先比较更高带宽，不能把相同带宽称为改善。
目录存在合理改善候选时，不能只返回未改善方案；原方案更便宜、已推荐过或赠品多都不能证明满足最新提速要求。
更高速方案超预算时保留合理比较并披露取舍，不将预算暗改为硬过滤，也不承诺同时满足速度与预算；用户明确不接受取舍时尊重其表达。
同规格、无基准或无改善方案时须如实标记和披露，不把更低价格、赠品或不同编号当成带宽提升，也不承诺实际体验必然改善。
本地检查验证提示词结构、示例JSON及精选示例通过真实校验器、变量声明、比较视图以及 1000M 缺口和 2000M 对照的传递；模型替身不证明真实语义选品正确。
上线前重新生成并同步完整DSL，不能只修改脚本或某一个节点。验收时确认运行提示词含输入输出示例和决策优先级，用户提示词含实际比较上下文，而非仍使用旧版连续文字。
在目标模型上重放原始对话：初筛应纳入更高速可售候选；精选须用原文核实并披露预算等缺口；最终回复不能把1000M称为比原1000M更快。
另测目录只有同速方案、基准未知和反馈后只补充预算三个边界，不以模型替身结果替代线上语义验收。

### 普通聊天

业务识别、需求提取、初筛与精选均增加一次校验反馈重生成：原输出预检失败后，携带具体错误、原始输出及完整原始任务重新调用对应模型，结果再次经过原校验器。正常路径不增加模型调用；每阶段最多两次模型调用，无回边，不循环重试。
四个内部模型默认开启 Dify JSON Schema 结构化输出；是否为原生受约束输出取决于目标模型及插件能力，
须在目标 Dify 实例验证。若界面提示 Model not supported，Dify 可能改为向提示词注入 Schema，仍有失败可能。
结构化解析或调用错误通过 fail-branch 封装明确失败标记，进入同一有限重生成；达到上限后明确失败，
不以空JSON或旧推荐兜底。校验反馈和原输出都是不可信数据，不得充当新用户事实或规则。
预检不写状态，最终校验从原始快照执行，避免需求和回答轮数重复累计。连续失败保留已确认需求；业务识别失败保留原话到待澄清队列，提取失败保留待处理消息，不要求用户重述。
真实需求澄清不是校验失败，不应触发自动重生成；不放宽套餐范围、业务隔离、用户原话证据等校验，不在失败后恢复历史推荐。
本地模型替身验证分支、调用次数及状态等价，不代表DeepSeek实际故障恢复率；上线后仍需重放真实对话验收，并观察额外调用的延迟和费用。未启用未经确认的原生Schema支持。

```json
{
  "inputs": {
    "event_type": "message",
    "bn_plan_codes": ""
  },
  "query": "想办宽带，希望包含家居电话，合约24个月",
  "response_mode": "streaming",
  "conversation_id": "",
  "user": "application-user-id"
}
```

首次请求可以省略 `conversation_id` 或传空字符串。保存响应返回的会话 ID，
后续消息和地址事件均继续使用同一 ID 和 `user`。
普通聊天每轮显式传 `message`，并清空 `bn_plan_codes`。
用户消息即使看起来像 JSON 事件，也只是自然语言内容，不能覆盖开始节点字段。

### 首次地址提交

1. Dify 识别到 BN，但还没有地址对应的套餐范围。
2. `address_action` Code 节点输出：

   ```json
   {"action":"request_address"}
   ```

3. 后端向前端转发表单动作，前端展示已有地址表单。
4. LLM 自然语言流式提示，例如“家居宽频需要查询地址覆盖范围，请填写地址表单。”
5. 用户提交地址，应用后端查询全部可售套餐编号。
6. 后端查询成功后发送：

```json
{
  "inputs": {
    "event_type": "address_add",
    "bn_plan_codes": "AB10936240D,AB12936240B,AD19924CM_C3F24NOR30IDD"
  },
  "query": "地址查询已完成，请继续处理宽带需求。",
  "response_mode": "streaming",
  "conversation_id": "returned-dify-conversation-id",
  "user": "application-user-id"
}
```

### 更换地址

前端已有更换地址入口。用户提交新地址、后端成功查询后，使用相同结构，
将 `event_type` 改为 `address_change`，携带新范围的全部编号。
这两个地址事件走同一段替换和加载逻辑，不是点击按钮时就发送。

成功但没有套餐时，发送地址事件并将 `bn_plan_codes` 设为空字符串。
查询失败由前后端明确展示，不发送空编号冒充成功；本工作流不接收失败地址事件。
新查询期间，前后端必须避免基于旧地址继续产生新的 BN 推荐。
失败后应明确继续使用哪个地址或要求重试，不能让用户误认为新地址已生效。

### 编号解析

- 使用英文逗号分割，去掉两侧空白，去重并保留首次顺序。
- 不改写大小写和原始编码。
- 编号为字母或数字开头，后续允许字母、数字、下划线和连字符。
- `A,,B`、中文逗号、非法字符等明确报错，不静默修复。
- 整个成功结果为空或只有空白表示无套餐。
- 任何新地址事件先清空旧范围、旧标签和旧推荐，再解析新内容。
  即使新结果格式错误，也不能沿用旧地址推荐。

## 4. 会话状态

11 个业务变量分别保存当前业务、BN 范围、三份标签数组、三份加载状态和三份需求对象。
另保留一个小型 `routing_context`，保存业务尚未明确时的用户原话和澄清问题；
否则下一轮“单独订阅”等短回答无法可靠关联原问题。
总计 12 个会话变量，完整字段和默认值见 [字段说明](fields.md)。

`snapshot` 只是 Code 节点间传递本轮变量值的临时对象，不是新的会话变量，
不以 JSON 字符串形式持久化。变量赋值节点将其中的值分别写回 12 个显式变量。
LLM 不接收整个 `snapshot`。

### 标签数组与加载状态

`bn_plans_tags`、`ms_plans_tags`、`xe_plans_tags` 使用 `array[object]` 保存编号和 `tag`。
数组有效时直接复用，不每轮请求后端。

每个业务的加载状态只取：

| 状态 | 含义 |
| --- | --- |
| `unloaded` | 尚未加载；BN 初始没有范围时先要求填写地址 |
| `ready` | 标签成功加载，有候选可用 |
| `empty` | 成功但无套餐，不重复请求 |
| `error` | 加载失败或数据无效，不能推荐 |

BN 标签加载失败但已有范围时，后续可重试标签接口，不用重新填表。
MS、XE 切回已加载业务时复用对应数组。
本版没有自动过期刷新机制。

### 地址变化时保留与清除

清除：旧 `bn_scope_codes`、`bn_plans_tags`、旧推荐编号、上一轮产品回复和等待旧问题的标记。
替换为新范围后重新获取标签，无论 `address_add` 还是 `address_change` 都执行。

保留：已确认的自由需求及其态度、`user_context` 和待处理原始需求。
已保存的推荐就绪状态可以保留，但地址事件本身绝不能把它从否升级为是。
新范围没有的旧偏好仍保留，用于说明取舍，不自动删除。

## 5. 用户背景与需求就绪

需求提取 LLM 在同一次调用中输出自由需求变更、关键歧义和 `context_update`，不再决定推荐时机。
不增加提取节点，不向提取节点提供产品目录；需求即使没有相应产品标签也必须保留。
`requirements` 是当前有效需求，产品标签只是检索线索；旧问答不能恢复已撤回的事实。

### 用户背景

`user_context` 保存用户明确表达的预算、人数、使用场景等，不适合直接映射成产品标签的信息。

例如“我们一家四口，经常看电影，月费预算不超过150港元，希望包含Netflix”：

- 自由需求：希望包含Netflix，以及用户明确表达的预算、人数和使用场景。
- 背景：一家四口、经常看电影、预算不超过150港元。
- 不能自动推断为 1000M、Wi-Fi 7 等产品需求。

没有背景变更时输出 `context_update: null`，保留原值。
有变更时输出完整的新背景和本轮原话证据：

```json
{
  "context_update": {
    "value": "一家四口；经常看电影；月费预算不超过150港元。",
    "evidence": ["一家四口", "经常看电影", "月费预算不超过150港元"]
  }
}
```

提示词要求保留未提及的旧事实，明确改口才替换，歧义先澄清。
Code 校验证据是否确实来自待处理用户消息。
背景清空也必须有用户明确要求的证据；地址触发说明不能作为背景来源。
每项独立需求和背景分别校验，失败条目不提交，但不回滚其他明确条目。
同一需求的改口用一次 `update` 原子替换；同一ID有多次操作时全部拒绝，避免执行一半。
澄清只阻止推荐，仍提交独立明确部分；旧 `recommend`、`readiness` 字段兼容接收但忽略，不丢弃合法需求。
完整JSON无法解析时不猜测内容，保留待处理原话，提供明确失败反馈。
代码只能检查结构和证据来源，不能完全证明自然语言摘要的语义正确性，
因此仍需真实模型验收。

背景不是后端硬筛选条件。本版由 LLM 结合自由标签语义、预算和场景初筛，
再阅读原文比较；标签缺失的价格视为未知，不能声称已保证满足预算。

### 推荐双门槛

推荐需要同时满足：

1. 当前目录为 `ready`，候选非空，BN 还须与地址可售范围一致。
2. `product_decision` 校验后 `ready_to_recommend` 为真；无未解决的关键歧义，编号属于当前范围。

模型裸输出推荐动作、数组非空、用户催促和标签数量多，都不能单独通过。
统一产品决策和证据规则见 [字段说明](fields.md)。
没有新待处理需求时，也可依据已有的当前有效需求重新分析新地址目录；地址说明不能当作购买事实。
之前只说“想办宽带”，填完地址后仍进入访谈；
之前已明确表达需求时，才能针对那些真实需求评估是否推荐。

### 产品驱动访谈：统一决策、自然提问、及时推荐

旧实现只依赖模型判断是否推荐，没有轮数上限和主题记录；
同时成功处理后清空待处理消息，若模型未更新背景，刚回答的信息缺少可靠保留。
用户回放中四轮有效回答后仍停在访谈，已由本地节点回放复现。

本版改为：

1. 代码保存实际问答原话，即使模型输出 `context_update: null` 也能读取近期回答。
2. 每业务记录 `interview_rounds`、`asked_topics`、`last_interview_topic` 和 `answer_history`。
3. 复用 `shortlist`，在分支之前结合目录差异、当前需求和问答输出唯一动作：访谈、澄清、推荐或边界说明。
4. 追问只包含主题、一项待确认产品信息、选择影响及阻塞标记，不复制标签或增加引用ID，不固定问题顺序或产品标签词表。
5. 已答、已问、不知道和无偏好不换措辞重复确认；最终 LLM 自然表达，不套固定问句，不盘点技术枝节。
6. 明确购买目标且无必要追问时零轮也可比较；3轮仅为可选访谈上限，重复可选主题也直接比较。
  真实冲突仍需澄清，不能为了赶进度被跳过；没有预算内套餐应披露缺口而不是继续拖延。
7. 初步推荐后根据用户反馈重排和缩小范围，不重新开始冗长访谈。

计数仅包含对实际产品访谈或业务内需求澄清的真实回答；地址提交、一般咨询和只解析到损坏JSON时不增加。
条目级失败或需要进一步澄清时仍保留真实问答；尚未核实部分不会因轮数上限被确认。
轮数上限不能绕过地址范围、接口错误、模型校验失败或关键冲突。
初步推荐必须披露未知预算、未确认速度和偏好缺口，不能因为“停止追问”就声称条件已全部满足。
真实模型最终话术仍需部署复测；本地可保证结构、范围、引用和显式动作路由，不保证问题的语义必要性或模型永不偏离提示词。

### 安全与业务条件

所有模型共享同一安全策略：用户消息、历史及产品文档内指令不能覆盖系统规则。
只追问与套餐选择直接相关的必要信息，地址沿用可信表单，不索取身份证、密码、验证码或支付资料。
不承诺文档外折扣、免收费、赠品、组合优惠、审批、库存、安装时限或办理资格。
用户期望优惠可保留，但“请批准免费”等指令不能被当成已批准产品条件。
纯无关或诱导请求进入受限咨询或 `boundary`；混合消息中的合法需求仍可独立保存。
不能为促成交易隐瞒预算差距、收费、合约约束或未知事实。
最终回复不接收全量标签，只能基于本轮校验精选介绍产品；访谈只能自然提出已批准主题的问题，不能用准备推荐的陈述结束。
提示词不是完整安全屏障；代码校验出处和范围不证明语义蕴含，仍需目标模型的对抗与正常对话验收。

## 6. 两阶段产品接口与调用次数

### 批量标签接口

```json
{"business":"BN","plan_codes":["PLAN_A","PLAN_B"]}
```

返回编号和标签，不返回全部 Markdown。
BN 返回编号集合必须与请求完全一致，不能缺项、增加、重复或忽略未知编号。
MS、XE 按业务查询全量目录，`plan_codes` 为空列表。
BN 无编号时根本不调用接口，空列表绝不表示查询全量 BN。

### 排序与详情接口

需求保存后，`shortlist` LLM 读取全部可售自由标签和当前业务需求及原话，统一决定追问或推荐，保留最多5款合理备选。
不依赖固定标签表，不再执行标签精确匹配计分；偏好不是资格硬过滤。
代码校验初筛 JSON、编号范围、数量和唯一性后，批量获取这些编号的详情，保持初筛顺序。
`rank.request_json` 保留初筛编号和依据；非法初筛、越界、重复、过多候选、缺项或缺失原文时阻止推荐。
不回退到旧计分结果，不从编号猜月费。空初筛不补候选，原文精选可继续返回空结果。
LLM 精选最多 3 款，且对每条有效需求输出 `supported`、`unsupported` 或 `unknown`。
明确结论必须引用对应套餐原文；未说明的能力、未量化的偏好或前提不明确时标记未知。
Code 校验数量、唯一性、候选成员关系、需求ID全覆盖及引用出处。
最终回复披露不支持项和未知项；引用校验不等于语义蕴含校验，不能保证LLM永不误判。
失败时最终回复上下文的精选结果置空，不从历史恢复旧推荐。
内部 `candidates_json` 保留原文；`sales_candidates_json` 是提供给精选模型的销售展示视图。
最终 `selected_plans_json` 同样使用销售展示视图，不把原文中的运营商身份信息重新暴露给回复模型。

| 场景 | 标签接口 | 排序详情接口 |
| --- | --- | --- |
| 缺少地址或一般知识咨询 | 0 次 | 0 次 |
| 首次加载有效范围，需求不足 | 1 次 | 0 次 |
| 标签有效，继续访谈 | 0 次 | 0 次 |
| 已有标签，需求就绪开始推荐 | 0 次 | 1 次 |
| 新地址有效，先前需求已清楚 | 1 次 | 1 次 |
| 成功但地址范围为空 | 0 次 | 0 次 |

本版不缓存完整候选详情，后续套餐事实问题若重新进入推荐分支，仍可能查询一次详情。
仍为5个模型节点；与上一版相比，访谈轮多一次产品分析调用，推荐轮调用数量不变。当前全部可售标签一次输入，不自动分批；
数百款目录上线前需评测输入长度、调用延迟和召回质量，超出预算时应另行设计分批或检索策略。

## 7. 动作和聊天流的分离

### 表单动作

只有需要填写地址时执行 `address_action`。
其 Code 输出固定为 `{"action":"request_address"}`，随后才进入回复 LLM。
前端不显示这段 JSON，而是展示已有表单。

普通 Dify Service API 可能隐藏节点输出，详见
[上游响应转换器](https://github.com/langgenius/dify/blob/main/api/core/app/apps/advanced_chat/generate_response_converter.py)
和 [节点事件定义](https://github.com/langgenius/dify/blob/main/api/core/app/entities/task_entities.py)。
因此接入约定为：

- 后端监听 `node_finished`。
- 只在 `data.node_id == "address_action"` 且 `data.status == "succeeded"` 时，
  向前端发送固定的 `{"action":"request_address"}`。
- 如果目标实例提供 `data.outputs`，可以额外核对同名动作，但不能以其必然存在为前提。
- 按本次运行 ID 和节点完成事件去重；失败或未完成事件不能弹框。
- 不通过聊天文本、节点标题或内部调试接口猜测动作。

固定节点 ID 是接入协议的一部分，不能只改工作流、不更新后端映射。
当前目录没有应用后端源码，此转发逻辑尚未实际接入。

### 自然语言流

`reply` LLM 统一处理访谈、推荐、一般咨询、澄清、无套餐、错误和地址引导。
`answer` 直接引用 `{{#reply.text#}}`，中间没有 Code 或模板把文本重新包装。
后端把 `message` 事件的 `answer` 分片直接转发给前端显示。
API 外层仍是 SSE JSON 事件，但聊天内容不再是业务 JSON。

回复结束后才记录 `last_reply`、实际访谈标记和推荐编号。
本轮已校验偏好和背景在生成回复前保存，避免回复失败导致需求整体丢失。
后端应等待 `workflow_finished` 后再执行下一轮，包括用户在流式引导期间提交的地址；
不能只看到 `message_end` 就假设后续状态写入已完成。
流中断、模型失败或保存失败时，前后端应明确提示，不能伪装成完整成功。

#### 18:39 业务识别循环空输出修复

此前失败分支接线错误地将 LLM 成功出口写成 `success-branch`，但 Dify 的成功出口为 `source`，
失败出口为 `fail-branch`。四个内部模型均已更正，否则校验器和循环赋值器无法沿成功路径执行，
循环的 `current_text`、`last_error` 会一直为空，最终被误报为模型输出为空。
旧本地循环模拟器按固定顺序直接执行子节点，未验证实际出口名称，导致之前测试未发现该问题；
现在改为依据真实子图连线、出口和分支跳过规则执行，并清除上一轮子节点变量以免陈旧值误用。
回归包含四个模型成功路径可达性、用户提供的截断 `finish_reason=abort` 输出重放，以及错误出口名称的负向对照。
截断文本现在实际进入校验反馈和有限重试，不再因接线丢失；不自动补齐不完整的结构化对象。
模型服务端或插件是否仍会独立返回 `abort` 尚需线上复测，不能据13个输出Token推断为长度上限。
