# 多业务工作流减重

## 业务规则

| 场景 | 预期行为 |
| --- | --- |
| 识别业务 | 区分 BN 家居宽频、MS 流动通讯及 XE 影音串流。附带权益跟随主业务。业务有歧义时保留客户原话并追问。 |
| 查询宽频地址 | 缺少地址可售范围时触发表单。收到地址结果后继续原选购请求。地址变更后清除旧目录和展示结果。 |
| 理解需求 | 按业务保存明确修改的要求。单轮查询可以使用临时条件。继续选购时沿用有效条件，查看其他套餐时排除已展示套餐。 |
| 核对套餐 | 从本轮业务的可售标签中初筛最多五款，只加载入选套餐原文。核验需求、条款引用和办理条件后最多展示两款。 |
| 交付结果 | 选购时输出已核验的套餐和办理入口。普通查询只回答事实。明确索取单款入口时先唯一定位并核验。正文、入口和后续指代使用相同的套餐顺序。 |
| 处理异常 | 结构化模型结果或调用失败时最多重试两次。核验失败时使用固定提示，动作输出 `NONE`。保留已通过校验的会话状态。 |

前端继续使用 `request_address` 和 `product_link_action`。正文由现有 Answer 节点流式输出。目录和原文沿用仓库内的模拟接口。

## 实施边界

- 将目录缓存判断、按需加载和校验合并到一个代码节点。
- 统一回复分支的数据结构。会话字段在分支输出中直接展开，本轮详情用 JSON 字符串传递。现有会话变量及其字段继续使用原类型。
- 将重复的确定性规则收敛到可维护的 Python 源码。构建时将各节点所需的代码和模拟目录嵌入 Dify DSL。
- 用真实 DSL 连线回放跨业务、地址切换、会话迁移、继续选购、历史归档和失败重试。每个执行到的代码节点都检查输出深度。

## 故障复现

11 月 26 日提交的 Langfuse 导出包含 17 次运行。5 次因对象深度超限失败，其中 4 次停在 `merge`，1 次停在 `scope_reply`。用导出中的节点输入回放旧版，超限发生在 `bundle.snapshot.<业务>_needs.active_selection.turn_requirements[0]`。另有 2 次因对象和字符串的类型冲突失败，分别涉及需求决策输入和缺地址分支。

Dify 默认限制 Code 节点输出的对象嵌套深度为五层。[Dify Code 节点限制](https://docs.dify.ai/en/self-host/use-dify/nodes/code)

本地回放已使用新 DSL 的入口迁移及受影响的实际代码节点验证上述 7 次运行的失败路径。连线测试检查所有执行到的代码节点，输出深度最多四层。线上导入及真实模型调用待验证。
