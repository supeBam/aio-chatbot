# AIO 多业务工作流接手指南

本文面向首次接手 Dify 工作流的同学，说明代码节点和 LLM 节点各自负责什么、节点之间如何协作，以及修改时需要保护的边界。

## 1. 工作流概览

主工作流定义在 [AIO Multi Business Structured.txt](<./AIO Multi Business Structured.txt>)，是一个 Dify Advanced Chat 应用。它面向三类新购产品：

- **BN**：家居宽带；候选范围受地址查询结果限制。
- **MS**：移动通讯。
- **XE**：影音/串流等产品。

工作流的核心原则是：**LLM 负责理解和提出结构化判断，代码节点负责校验、状态管理、产品范围限制和事实核对**。最终给用户的自然语言由最后一个 LLM 节点生成并流式输出。

```text
用户消息/地址事件
  → 校验输入与会话状态
  → 识别业务（地址事件直接进入 BN）
  → 加载或复用当前业务的产品标签
  → 解析需求并更新会话状态
  → 决定追问、澄清、拒绝范围外请求或推荐
  → 校验候选编号并取得候选套餐原文
  → 按需求逐项核对原文并验证推荐
  → 准备上下文
  → 流式生成自然语言回复并记录状态
```

工作流里标注为 `mock` 的代码目前模拟后端接口。离线套餐标签生成工具见 [plan_catalog.py](./plan_catalog.py)；结构化模型输出的 JSON Schema 定义见 [model_output_schemas.py](./model_output_schemas.py)，相关构建逻辑见 [build_structured_variant.py](./build_structured_variant.py)。

## 2. LLM 节点

表中的**画布标题**是 Dify 编辑器节点卡片上显示的名称；**节点 ID** 是工作流配置中的技术标识，用于变量引用和连线。新人在 Dify 画布上找节点时，优先按标题查找。

| 画布标题（Dify 显示） | 节点 ID（配置标识） | 作用 | 主要输入与输出 | 后续代码校验 |
|---|---|---|---|---|
| 识别业务，不混淆附带权益 | `business` | 识别本轮业务、意图及是否需要澄清。特别处理“套餐加上某权益”等表述，避免误判为已有服务加购。 | 输入当前消息、当前业务和待澄清上下文；输出业务、意图、提及业务及业务请求。 | “校验模型结果，不写入会话”（`business_validation`）校验结构和业务值；“按业务保存待处理需求与澄清状态”（`prepare`）再决定下一步路由。 |
| 独立理解用户需求、态度和改口 | `extract` | 从本轮对话中提取需求变化、用户态度、优先级、背景及需要澄清的问题。 | 输入当前业务、事件、需求状态和实际问答；输出 `changes`、`question_changes`、澄清信息等。 | “校验模型结果，不写入会话”（`extract_validation`）校验模型输出；“按条校验并保存需求，交由产品分析决策”（`merge`）逐条验证并合并需求状态。 |
| 依据产品差异统一决定追问或推荐 | `shortlist` | 综合已确认需求与当前业务全部可售套餐标签，统一决定推荐、继续访谈、澄清或说明能力边界。 | 输出动作、最多 5 个初筛套餐编号、追问信息和理由。 | “校验模型结果，不写入会话”（`shortlist_validation`）处理结构/校验反馈；“校验追问结构、产品范围及统一动作”（`product_decision`）再验证动作、追问和套餐范围。 |
| 逐需求核对套餐原文并精选最多三款 | `select` | 阅读候选套餐的完整原文，逐需求判断套餐是否支持、未知或不支持，并从中精选最多 3 款。 | 输入需求、比较上下文和候选套餐原文；输出各候选的逐项 `assessments` 和理由。 | “校验模型结果，不写入会话”（`select_validation`）校验输出；“校验套餐、需求覆盖及原文引用”（`validate_selection`）检查套餐编号、需求覆盖和原文引用。 |
| 自然语言回复，直接流式输出 | `reply` | 根据已确定的模式、需求、候选结果和产品标签生成面向用户的自然语言回复。 | 接收“准备流式回复上下文，不包装聊天JSON”（`reply_context`）整理好的上下文；输出普通文本并直接流式给用户。 | “完整回复后记录本业务上下文”（`record_reply`）在回复完成后保存实际回复及访谈状态。 |

前四个 LLM 节点使用结构化 JSON 输出，并有对应的校验与重试路径；`reply` 是最终自然语言节点，不属于前述结构化 JSON 决策链。

## 3. 代码节点

代码节点不是“另一个 LLM”：它们执行确定性逻辑，包括输入检查、JSON/字段校验、业务范围约束、会话变量整理、套餐数据处理和失败恢复。以下按执行阶段列出当前代码节点。

### 3.1 输入、地址和业务路由

| 画布标题（Dify 显示） | 节点 ID（配置标识） | 职责 |
|---|---|---|
| 校验事件、替换地址并使旧产品数据失效 | `ingress` | 检查事件类型和会话快照，规范化输入；处理地址新增/变更事件，并让已过期的产品范围或目录数据失效。 |
| 准备入口错误话术 | `input_failure` | 将入口校验失败整理成统一错误回复上下文，避免无效输入继续进入产品决策。 |
| 地址事件固定进入BN | `address_business` | 地址事件直接构造成 BN 业务结果，不交由业务识别模型重新判断。 |
| 校验模型结果，不写入会话 | `business_validation` | 校验“识别业务，不混淆附带权益”的结构化结果及允许值；失败时生成校验反馈供重试，不在此节点提交会话状态。 |
| 按业务保存待处理需求与澄清状态 | `prepare` | 根据已校验的业务识别结果更新/准备当前业务、意图和待处理状态，产出后续路由需要的结果。 |
| 准备业务澄清或识别错误 | `scope_reply` | 为业务不明确、需要澄清或识别失败的分支准备回复上下文。 |

### 3.2 产品目录加载与前置分流

| 画布标题（Dify 显示） | 节点 ID（配置标识） | 职责 |
|---|---|---|
| 检查标签数组，决定是否加载 | `catalog_context` | 根据业务、地址范围、目录缓存状态和咨询/选购意图，判断是否需要加载标签或可否直接短路。 |
| 模拟接口一：批量获取套餐标签 | `fetch_tags` | 模拟批量获取套餐标签；BN 结果需与地址可售编号范围一致。 |
| 复用数组，不请求后端 | `cached_tags` | 复用已存在的标签数组，不重复请求模拟接口。 |
| 校验并保存当前业务产品目录 | `catalog` | 验证并保存当前业务目录，生成后续处理所需的目录 JSON、状态和指令。 |
| 准备表单、空结果、失败或一般咨询 | `pre_reply` | 为地址表单、空结果、失败或一般咨询等无需走完整推荐的情形准备回复上下文。 |

### 3.3 需求提取与决策输入

| 画布标题（Dify 显示） | 节点 ID（配置标识） | 职责 |
|---|---|---|
| 校验模型结果，不写入会话 | `extract_validation` | 校验“独立理解用户需求、态度和改口”的模型输出并整理错误反馈；不把未经后续处理的模型内容直接当成最终会话状态。 |
| 按条校验并保存需求，交由产品分析决策 | `merge` | 逐条验证需求/问题变更，并将有效结果合并到对应业务的需求状态，供产品分析使用。 |
| 提取并保存本轮需求状态 | `decision_state` | 从会话需求和目录中构造决策输入，例如已确认需求、问答上下文及与上轮推荐的比较信息。 |

### 3.4 产品动作、候选套餐与原文核验

| 画布标题（Dify 显示） | 节点 ID（配置标识） | 职责 |
|---|---|---|
| 校验模型结果，不写入会话 | `shortlist_validation` | 校验“依据产品差异统一决定追问或推荐”的模型输出，并整理重试反馈。 |
| 校验追问结构、产品范围及统一动作 | `product_decision` | 对追问结构、动作、业务和套餐编号执行最终代码侧校验，形成明确的本轮动作。 |
| 缺地址、错误或一般咨询不执行产品决策 | `skip_analysis` | 对缺少必要地址、已有错误或一般咨询等分支保留原上下文，不继续执行产品决策。 |
| 保存本轮已校验产品动作 | `product_state` | 保存通过校验的产品动作和回复模式，供后续分支使用。 |
| 校验初筛编号并批量获取最多五款详情 | `rank` | 再次核对初筛套餐编号及候选范围，并模拟批量取得最多 5 款套餐的完整销售原文。 |
| 校验模型结果，不写入会话 | `select_validation` | 检查“逐需求核对套餐原文并精选最多三款”的模型输出结构及输入关联；整理错误信息或生成后续验证使用的结果。 |
| 校验套餐、需求覆盖及原文引用 | `validate_selection` | 最终验证套餐是否属于当前候选、需求是否逐项覆盖，以及引用是否能在候选原文中找到。 |
| 推荐出错时清空事实，禁止历史兜底 | `recommendation` | 汇总套餐获取和精选的结果；发生错误时清空推荐事实，不以历史推荐作为兜底。 |
| 传递非推荐回复上下文 | `basic_reply` | 将非推荐分支的回复上下文直接传给最终回复准备阶段。 |

### 3.5 回复与会话记录

| 画布标题（Dify 显示） | 节点 ID（配置标识） | 职责 |
|---|---|---|
| 准备流式回复上下文，不包装聊天JSON | `reply_context` | 整理回复模式、用户原话、需求、目录和精选结果；准备供最终 LLM 使用的上下文，不把回复包装成聊天 JSON。 |
| 先输出前端弹表单动作 | `address_action` | 输出前端动作 `request_address`，由前端触发表单流程；不是聊天文本，也不应改成在聊天中索取完整地址。 |
| 输出套餐办理链接动作 | `product_link_action` | `answer` 后接收办理链接列表，输出 `frontend_action` 和 `products`。输入列表每项只含 `plan_code` 和 `link_label`，由 `reply_context` 根据本轮推荐或明确索取的唯一可售套餐生成。 |
| 完整回复后记录本业务上下文 | `record_reply` | 在最终回复后写回实际回复和访谈状态；供下一轮业务路由、需求理解及追问延续使用。 |

前端从当前运行中成功完成的 `product_link_action` 节点读取 `data.outputs`。`frontend_action` 为 `SHOW_PRODUCT_LINK` 时，按 `products` 的顺序在流式正文结束后展示入口。每项的 `link_label` 用于显示，`plan_code` 用于沿用现有跳转规则。无法生成有效地址的单项可以省略。无入口时动作是 `NONE`，`products` 为空数组。接入时需确认 SSE 通道会透传该节点的动态输出。

## 3.6 LLM 节点失败处理

| 画布标题（Dify 显示） | 节点 ID（配置标识） | 职责 |
|---|---|---|
| 记录模型节点失败并重试 | `business_node_failure` | 把“识别业务，不混淆附带权益”LLM 节点运行失败转成错误信息和重试标记。 |
| 记录模型节点失败并重试 | `extract_node_failure` | 把“独立理解用户需求、态度和改口”LLM 节点运行失败转成错误信息和重试标记。 |
| 记录模型节点失败并重试 | `shortlist_node_failure` | 把“依据产品差异统一决定追问或推荐”LLM 节点运行失败转成错误信息和重试标记。 |
| 记录模型节点失败并重试 | `select_node_failure` | 把“逐需求核对套餐原文并精选最多三款”LLM 节点运行失败转成错误信息和重试标记。 |

这些节点与各自的重试循环配合；结构化模型节点的配置最多重试 2 次。注意区分“模型调用失败”和“模型成功返回但内容不合规”：前者进入 `*_node_failure`，后者由相应的 `*_validation` 节点产生校验反馈。

## 4. 会话状态与关键数据流

主要会话变量按业务隔离：

- `current_business`：当前处理的业务。
- `bn_scope_codes`：地址查询后可信、可售的 BN 套餐编号范围。
- `routing_context`：业务尚未确定时保存的原话与澄清问题。
- `bn_needs`、`ms_needs`、`xe_needs`：各业务的需求、用户回答、已问主题、访谈轮次和上一轮回复等。
- `bn_plans_tags`、`ms_plans_tags`、`xe_plans_tags`：各业务的标签目录。
- `bn_catalog_status`、`ms_catalog_status`、`xe_catalog_status`：对应目录的加载状态。

理解数据流时，可先沿这条主链查看输入输出（括号内是画布标题，代码为节点 ID）：

1. “校验事件、替换地址并使旧产品数据失效”（`ingress`）产出标准化事件、消息和状态快照。
2. 各“校验模型结果，不写入会话”节点把 LLM 输出变成可供代码消费的受检数据，并提供重试反馈。
3. “按业务保存待处理需求与澄清状态”（`prepare`）、“按条校验并保存需求，交由产品分析决策”（`merge`）、“保存本轮已校验产品动作”（`product_state`）和“完整回复后记录本业务上下文”（`record_reply`）在明确阶段更新对话状态。
4. “校验初筛编号并批量获取最多五款详情”（`rank`）提供候选完整原文；“校验套餐、需求覆盖及原文引用”（`validate_selection`）再检查 LLM 结论是否被原文支持。
5. “准备流式回复上下文，不包装聊天JSON”（`reply_context`）把业务结果转换成回复输入；“自然语言回复，直接流式输出”（`reply`）负责自然语言表达。

## 5. 修改时必须保留的边界

- **不要把 LLM 输出直接当事实或会话状态。** 保留结构校验、业务规则校验和状态写回的分层。
- **不要扩大 BN 候选范围。** 地址可售编号是范围约束；标签目录或模型输出不能替代该约束。
- **套餐事实必须来自本轮候选原文。** 标签用于初筛，不等于权威条款；不能让模型自行补充折扣、资格、费用或办理承诺。
- **不要用历史推荐填补本轮失败。** 推荐/套餐原文处理出错时应维持错误状态并清空推荐事实。
- **保留前端地址动作。** 缺地址时通过 `request_address` 触发表单流程，不要改成在聊天中收集完整住址。
- **修改结构化输出时同步检查 Schema 与校验器。** 尤其核对 [model_output_schemas.py](./model_output_schemas.py)、工作流内相应 `*_validation`/`validate_selection` 代码和 LLM 提示词中的字段是否一致。
- **修改节点输入输出时检查所有引用。** Dify 变量选择器、循环重试更新节点、条件分支和最终回复上下文都可能依赖同一字段。

## 6. 新人排查建议

建议在 Dify 运行记录中从入口开始沿节点追踪，而不是只看最终回复：

1. 确认输入事件及 `ingress` 的 `ok`、`event`、`active_business`。
2. 对照 LLM 的 `structured_output` 和紧随其后的代码校验节点，判断问题是模型误判还是校验拒绝。
3. 检查目录状态及 BN 的 `bn_scope_codes`，确认是否是地址范围或缓存导致的分流。
4. 查看 `*_needs` 和 `decision_state` 输出，确认需求是否正确合并、追问是否仍待回答。
5. 推荐路径检查 `product_decision`、`rank` 的候选原文及 `validate_selection` 的校验错误。
6. 最后检查 `reply_context` 输入和 `record_reply` 写回，确认回复内容及下一轮状态一致。

调试时可优先覆盖：业务不明确需澄清、地址表单/地址变更、目录复用、需求追问、套餐推荐、模型结构不合规重试、模型调用失败，以及套餐原文不支持需求等路径。
